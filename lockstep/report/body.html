1. Overview

Seven Java implementations were built and benchmarked: a lazy and a lock-free doubly linked list, a lazy lock-based stack and a Treiber stack, a two-lock queue and a Michael-Scott queue, and an elimination backoff stack built on the Treiber stack. All of them implement one small interface (read/insert/delete) so a single harness (Bench.java) drives every experiment. Check.java is a multi-threaded correctness test: it checks set semantics, that prev links mirror next links, and that every pushed or enqueued value is removed exactly once.

2. Implementations

2.1 Lazy doubly linked list (LazyDList)

The list is sorted, with sentinels head (MIN) and tail (MAX). Each node has key, volatile next, prev and marked, plus a ReentrantLock. A thread traverses next links without locking, locks pred and then curr, and validates !pred.marked && !curr.marked && pred.next == curr. If validation fails, it retries. Insert sets node.next=curr, node.prev=pred, then pred.next=node, then curr.prev=node. Delete first marks curr (logical deletion), then unlinks it (physical deletion) with pred.next=succ; succ.prev=pred. The prev links stay consistent because a node's prev is only written by a thread that holds the lock of that node's predecessor. While a thread holds curr's lock, nobody else can change succ.prev. contains() is wait-free and takes no locks.

2.2 Non-blocking doubly linked list (LockFreeDList)

This list uses the Harris-Michael design. Each next field is an AtomicMarkableReference, so the successor and the deleted mark change together in one CAS. Delete marks curr.next with compareAndSet(succ, succ, false, true) (logical deletion), then tries to unlink with a CAS on pred.next (physical deletion). attemptMark is deliberately not used: it returns true when the node is already marked, which would let two deleters both report success. find() helps other threads. Any marked node it passes is unlinked with a CAS. If that CAS fails, the traversal restarts from head, and every failed insert or delete CAS also retries. The prev pointers are updated after each successful link or unlink, but correctness never depends on them; the next chain is the authoritative structure. This avoids the multi-word CAS that a fully lock-free, symmetric doubly linked list would need. No locks appear on any update path.

2.3 Lazy lock-based stack (LockStack)

Push and pop read top without the lock and prepare the new node (node.next = observed). They then take the lock, check top == observed, and only then publish. If the check fails, they retry. A pop that reads an empty stack returns without locking. peek() is a single volatile read.

2.4 Treiber stack (TreiberStack)

top is an AtomicReference. Push links the new node to the observed top and tries CAS(top, oldTop, node). Pop tries CAS(top, oldTop, oldTop.next). Both retry when the CAS fails. Java's garbage collector prevents ABA, because a node cannot be reused while any thread still references it.

2.5 Two-lock queue (LockQueue)

The queue starts with a sentinel node and uses separate headLock and tailLock, so one enqueuer and one dequeuer can run at the same time. Enqueue appends under tailLock. Dequeue reads head and head.next without the lock. It returns empty if head.next is null; otherwise it takes headLock, checks that head is unchanged, and advances head. If the check fails, it retries.

2.6 Michael-Scott queue (MSQueue)

head, tail and every next field are AtomicReferences. Enqueue CASes last.next from null to the new node, then tries to swing tail. Any thread that finds tail lagging behind (tail.next != null) helps by advancing it. Dequeue CASes head forward. Peek reads head.next and retries if head changed meanwhile.

GC nepotism (both queues). In a first run of the experiments, queue runs overshot their deadline by up to 0.8 s, and throughput fell steadily over the life of each JVM. GC logs showed young-generation pauses of 125–160 ms and a live heap growing from 95 MB to 290 MB. The cause is that a dequeued sentinel promoted to the old generation still points to younger nodes and keeps them alive, so every young collection has to copy the entire queue history. Both queues therefore self-link the dead sentinel after a successful dequeue (h.next = h), as java.util.concurrent.ConcurrentLinkedQueue does. This is safe because any thread still holding the old node fails its head/tail check and retries. After the fix, the pauses disappeared and all queue experiments were rerun.

2.7 Elimination backoff stack (EliminationStack)

This class extends TreiberStack and reuses its single-attempt tryPush/tryPop. When a CAS on top fails, the thread backs off into an elimination array of 8 lock-free exchangers and picks a slot at random with ThreadLocalRandom. Each exchanger is an AtomicStampedReference with three states: EMPTY, WAITING and BUSY. The first thread CASes EMPTY to WAITING and spins. A partner CASes WAITING to BUSY and takes the waiting thread's item. Pushes offer their value and pops offer null, so a push that meets a pop completes both operations without touching top. Two pushes or two pops that meet simply retry. The backoff policy is a 2 µs timeout per visit, after which the thread goes back to the central stack.

4. Experimental methodology

  • Grid: 7 implementations × N ∈ {1,000, 10,000} × 3 workloads (0C-50I-50D, 50C-25I-25D, 100C-0I-0D) × threads {1,2,4,6,8,10,12,14,16} × 5 runs, for 1,890 timed runs in total.
  • Run duration (deviation from the brief): each timed run lasts 2,000 ms rather than the specified 10,000 ms, to fit the full grid into the available time on a single 4-core machine. The duration is a command-line parameter: scripts/run_all.sh 10000 5 reruns the whole grid at the specified 10 s. Because throughput is normalised by the measured elapsed time and every run has the same duration, throughput and speedup are computed exactly as specified.
  • Prefill: before timing, N/2 distinct keys (a shuffled subset of [0, N)) are inserted, pushed or enqueued. List keys are drawn from [0, N), so the 50/50 insert/delete mix keeps the list about 50% full.
  • Workload generation: before timing, each thread gets a pre-generated array of 218 (op, key) entries drawn with the workload's percentages. Threads cycle through it, so no random numbers are generated inside the timed loop.
  • Timing: each run uses a fresh structure. Threads are created and started first and then wait on a CountDownLatch. The main thread takes start = System.nanoTime(), publishes deadline = start + duration, and opens the latch. Each worker runs while (System.nanoTime() < deadline) and executes 64 operations per check, counting completed operations. The batching matters. On macOS, HotSpot's System.nanoTime() performs a CAS on one global word to guarantee monotonic time. We measured this capping all threads together at about 30 M calls/s at 1 thread, falling to 26 M at 4 threads. With one clock call per operation, every fast structure (stacks, queues, peek) saturated near 29 MOPS regardless of thread count, so the benchmark was measuring the clock rather than the data structure. Checking every 64 operations removes that artefact and overshoots the deadline by well under 1 ms of a 2,000 ms run (the measured elapsed time is used in any case). After all threads join, end = System.nanoTime() is taken. Only System.nanoTime() is used for timing.
  • Metrics: throughput (MOPS) = ops / (elapsed_s × 106). Pavg is the mean of the 5 runs, and speedup(p) = Pavg(p) / Pavg(1) for the same implementation, N and workload.
  • JVM: Java 17 HotSpot with -Xms2g -Xmx2g. One JVM is started per (implementation, N, workload), and a discarded 1-second warm-up run lets the JIT compile the hot paths first. JVM startup, prefill, generation and output are all outside the timed interval.
  • Hardware: a 4-core Intel Mac (macOS 13) with no SMT (hw.ncpu = 4). Every configuration above 4 threads therefore oversubscribes the CPU, and the OS scheduler time-slices threads. This shapes the results at 6–16 threads.

To reproduce: run scripts/run_all.sh, which compiles, runs the grid and resumes where it stopped. Then run python3 scripts/analyze.py, gnuplot scripts/plots.gp and python3 scripts/make_report.py. The raw data for every run is in results/raw/*.csv and results/all_runs.csv. Averages and speedups are in results/averages.csv.
